# Calibrating device behaviour with a human in the loop

How the seven backlight effect values were mapped to names, written down as
a method because the same shape recurs: **the machine can change the world
but cannot observe the result, and the human can observe but should not have
to drive.** Splitting those two roles cleanly is most of the technique.

## When this applies

Use it when a fact is only obtainable through human senses:

- what a keyboard's LEDs are actually doing
- whether an interaction *feels* right
- whether a glyph renders, or a colour follows the theme

It does **not** apply where a machine check exists. Reaching for a human to
confirm something `solaar show` could answer wastes the scarcest resource in
the loop.

## The roles

| | drives | observes | records |
|---|---|---|---|
| agent | ✅ | ❌ | ✅ |
| human | ❌ | ✅ | ❌ |

The human's entire job is to look and say what they saw. Every command,
every retry, and every write-down belongs to the agent. If the human is
copying commands or editing a table, the split has failed.

## The protocol that worked

**1. Make it machine-drivable before asking anyone to look.**
A single command per trial (`mx-backlight-effect set 4`) means the human is
never waiting on setup. Building the helper *first* is what turned this from
a negotiation into a series of one-line questions.

**2. Change exactly one thing per trial, and say what you changed.**
"Effect 4 is now active" is answerable. "I cycled through a few" is not.

**3. Label honestly until confirmed.**
The first build shipped `Effect 0`, `Effect 1`, `Effect 2`. A guess that
value 3 was "Wave" would have been worse than a number: a wrong label looks
authoritative, and nobody re-checks it later.

**4. Record each answer immediately, in code, with the observation as the
comment.** Not in a scratch note.

```js
// 4: only the keys being pressed light up.
4: "Reaction",
```

The observation *is* the justification. Six months later that comment is why
nobody "fixes" the mapping.

**5. Hunt for confounds before believing an answer.**
"Effect 1 is like off, no lights" arrived while the brightness happened to
be at level 1, the dimmest setting. Dim is not off. Re-testing at level 6
distinguished them — and the device then corroborated it independently by
*forcing the level back to 0*, which no amount of looking could have shown.

**6. Prefer corroboration to a single sighting.**
Value 5 was reported as Random twice, in different sessions, unprompted the
second time. Where the machine can cross-check a human observation, let it:
that is how "effect 1 is off" went from an impression to a fact.

**7. Let the machine close the loop where it can.**
By elimination, the last unmapped value had to be Wave — but it was applied
and confirmed anyway. Elimination is a hypothesis, not an observation.

## Anti-patterns, all of them learned here

**Timed capture windows.** Three captures were run as "press the key during
the next 45 seconds". All three came back empty, because a person is not a
scheduled job. The fix is state that persists: apply the effect and *leave
it applied*, so the answer can arrive whenever the human is next at the
keyboard. Sixty seconds of the agent's patience is free; sixty seconds of
someone else's attention is not.

**Negative results with no control.** An empty capture proves nothing unless
something known-noisy would have shown up in it. Adding the backlight keys
as a control is what made a later silence meaningful.

**Self-inflicted noise.** One capture drowned in traffic generated by *this
plugin's own* 300-second poll. Before trusting an instrument, check whether
you built something that pollutes it.

**Rounding partial verification up.** At one point six keyboard paths had
been implemented and three confirmed. "Keyboard navigation works" was not a
statement anyone had earned yet, and the task stayed open until all six were
pressed. Three of six is not two-thirds of a feature; it is an unknown.

**Asking a human to confirm what a machine can check.** Every question spent
on something scriptable is a question not spent on the thing only they can
answer.

## What it produced

Seven values mapped, each with the observation that identified it; the
"seven values for six documented effects" puzzle resolved (the seventh is
*off*, not a duplicate); and three bugs that only surfaced because a person
was looking at the hardware while the machine drove it:

- an effect that cleared the device's `enabled` flag, so the helper could
  strand the keyboard dark
- degraded reads returning zeros rather than errors, which would have
  silently hidden the feature
- the previous effect's last frame freezing on screen when switching to a
  static effect

None of those would have been found by a test suite, and all of them were
found in a single sitting.

## The shape, in one line

Make it drivable, change one thing, ask a question that can be answered in a
sentence, write the answer down where it will be read next time — and treat
"I could not observe it" as a different claim from "it did not happen".
